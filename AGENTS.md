# Agent rules
- Public voice ordering lives at /commander and calls the voice-order edge function (transcribe + map to Shopify catalog); checkout passes delivery details as Shopify cart attributes that shopify-order-webhook maps to order fields — keeps Shopify the single source of orders.
- Checkout navigation replaces the current top-level page using the Storefront API checkout URL; blocked embedded navigation exposes a user-clicked _blank link to that ready URL, with noopener/noreferrer and an explicit preview-only explanation — sandboxed previews forbid top navigation and Shopify forbids framing; never reserve blank tabs.
- Commander mobile scrolling uses a native scroll container with a separate overlay indicator, enabled only on mobile, to avoid changing desktop layout or reserving scrollbar space.
- Commander carts share a compact product row with an inline variant selector using the existing Storefront API independently of voice processing, so desktop and mobile controls stay consistent without altering listening or comprehension.
- Commander desktop/tablet (md+) share a three-column grid with adaptive tablet widths — narrow chat with accent mic, central list, right delivery and checkout; the welcome spans all columns — preserves one non-mobile presentation without touching voice processing.
- CommanderDesktopDelivery owns desktop/tablet delivery shortcuts and edit state; mobile retains CommanderDeliveryHints — isolates mobile presentation from other views.
- Commander mobile presentation lives in CommanderMobileExperience, with welcome/list screens and separate history/delivery drawers; Commander supplies the existing recorder, conversation and checkout handlers — isolates mobile layout changes from desktop and the locked voice pipeline.
- Commander order completion sends available delivery details straight to Shopify checkout as cart attributes without blocking for missing values; custom logistics fields require Shopify checkout customization, unlike native address/contact fields — no separate delivery screen; never changes voice processing.
- Commander suggestions use an independent authenticated rules service with server-side Shopify validation, public evaluation and idempotent offer tracking; this keeps recommendations separate from the locked voice pipeline.
- Client "Gestion de projet" (/projets) uses email accounts; orders link to clients by Shopify order email (RLS on jwt email) and to projects via cart attributes that shopify-order-webhook only accepts when the project owner's email matches — invoices are PDFs built client-side from webhook-stored prices, since Shopify exposes no invoice download.
- Staff portal access is gated by public.staff_accounts status plus user_roles; all approvals/suspensions go through the staff-access edge function (service role) — keeps role grants server-side.
- Admin client management reuses the client project view with scoped operations through admin-clients, which validates an active admin and client ownership server-side — grants cross-client management without impersonation or widening client RLS.
- Two portals: client pages live in src/portals/client, team (admin/supplier/partner) pages in src/portals/team, loaded lazily via TeamRoutes; team addresses show the plain NotFound page to non-team users; /connexion offers Client/Admin/Fournisseur choices linking to /equipe, and the shared AccountSwitcher (src/components) lets multi-role users switch spaces — client code never imports team code, and access stays enforced by TeamGuard.
- Shared AuthContext carries only the session; roles/profile load in TeamAuthContext inside the team portal — keeps role logic out of the client bundle.
- Client sub-accounts (client_members + client_project_members) resolve access through SQL security-definer helpers (client_ctx, client_can_view_project/order); invites go through client-team, which only emails after the invite_client_member RPC authorises with the caller's token — permission rules live in one place, the database.
- Client support chat uses support_threads/support_messages: clients write only through start_support_thread/post_support_message RPCs, staff reply through support-reply (stores + emails in the Gmail thread), and poll-supplier-emails routes client replies to RenoCart's own order confirmation (sent by shopify-order-webhook) into the thread — supplier and client conversations stay separate.

- Admin supplier/client inboxes share a team-only messaging provider and per-user database read receipts; Overview windows reuse the full chat pages in compact mode so sending, proposals and attachments keep the same behavior.
- Client pages share ClientHeader (Commander, Mes projets, Notre équipe, À propos, Connexion/Déconnexion; mobile uses a side menu) — one navigation for all client views; À propos/Notre équipe copy is mirrored from renocart.ca.
- Commander size substitution is isolated in supabase/functions/voice-order/substitution.ts (SUBSTITUTION_ENABLED flag) and src/portals/client/components/CommanderSubstitution.tsx — the user asked that this feature be revertible alone without touching anything else.
